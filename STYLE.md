# $bog_gamengine — как писать код

Общие правила мола в `bog/mol_skill/references/STYLE.md`: имена, отсутствие
комментариев, коммиты `$bog_gamengine_x: что изменилось`, дерево делает максимум.
Здесь только то, что добавляет движок.

## Холодное и горячее

Прежде чем завести свойство, ответь: это вещь или масса?

- Вещь: `@$mol_mem` в `$mol_object2`, читается кем угодно, пишется из `step`.
- Масса: элемент `Float32Array` в `batch`, читается только `draw`, пишется в `fill`.

Признак ошибки: `@$mol_mem_key` с числовым ключом на тысячу значений. Это масса,
переноси в буфер.

## Горячий путь без аллокаций

Внутри `step`, `fill`, `phys.step` и функций `vec`:

- ни `new`, ни литералов массивов и объектов, ни `.map`/`.filter`/spread;
- результат пишется в переданный `out`, функция возвращает его же;
- циклы `for` по индексу, не `for of` по итератору;
- временные векторы это поля класса, созданные один раз.

```ts
step( dt: number ) {
	const vel = this.vel()
	const pos = this.pos()
	$bog_gamengine_vec_scale( this.tmp, vel, dt )
	$bog_gamengine_vec_add( pos, pos, this.tmp )
	this.pos( pos )
}
```

Вне горячего пути обычный мол: аллокации в мемо не страшны, они один раз.

## Правка на месте и мемо

`this.pos( pos )` с той же ссылкой инвалидацию не даст. Это осознанно для горячего
пути. Если свойство читает HUD или другой холодный узел, пиши новую ссылку или
держи рядом счётчик версии. Правило: **позиция героя это новый `Float32Array` на
запись, позиции пуль это правка буфера батча.**

## GL только в `draw`

`gl.` встречается в `draw` и нигде больше. `shader` отдаёт строки, `shape` отдаёт
массивы, `atlas` отдаёт картинки, `batch` отдаёт буферы. Кто хочет нарисовать
что-то новое, добавляет шейдер и фигуру, а не draw-вызов.

Внутри `draw` GL-объекты создаются только в мемо по ключу и никогда внутри
`paint()`. `paint()` только выставляет состояние, заливает буферы и рисует.

## Шейдеры

- Точка входа программы это строка в `vert()`/`frag()` класса шейдера. В `.glsl`
  файлы точки входа не кладут, причина в архитектуре, раздел 3.1.
- `.glsl` файлы только в `glsl/`, только функции с аргументами, префикс
  `bog_gamengine_`, без обращения к юниформам и атрибутам.
- Имена в `face` в `snake_case`: `proj`, `view`, `vertex`, `uv`, `normal`,
  `inst_*`, `pipe_*`, `color`.
- `face` объявляется `as const`, тип программы выводится из него, строковые ключи
  в `glob()`/`param()` проверяет компилятор.

## Узлы и дерево

Сцена демо описывается в `view.tree`, как любой мол-компонент:

```tree
Scene $bog_gamengine_scene
	kids /
		<= Hero $bog_gamengine_sprite
			atlas <= Atlas
			frame \hero
			pos? <=> hero_pos?
		<= Coin* $bog_gamengine_sprite
			atlas <= Atlas
			frame \coin
			pos <= coin_pos*
```

Логика поведения это `step( dt )` в `.ts` наследника узла, не колбэк в дереве.
Узел не знает про ввод напрямую: он читает `input.action( 'jump' )`, а кто и как
это действие включает, решает приложение.

Никаких `.make({})` с замыканиями внутри `step`: узлы создаются деревом или
`@$mol_mem_key` фабрикой, как `Coin*`.

## Единицы

Метры, секунды, радианы. Скорость в единицах в секунду, умножается на `dt`.
Число «за кадр» в коде это ошибка.

## Тесты

- Один тест на одно утверждение, имя теста и есть описание.
- Математика и физика тестируются в ноде через `$mol_assert_equal` с округлением
  до 1e-6 там, где есть тригонометрия.
- Рендер через `bog/probe`, только цвет пикселя и счётчики вызовов, никаких
  скриншотов.
- Тест не трогает `document.body` (см. память о демке, пустеющей на `test.html`).

## Что не делать

- Не заводить `index.html` нигде, кроме `demo/`.
- Не тащить `$mol_3d_*` напрямую в `demo`: если демо чего-то не хватает в движке,
  добавляется модуль движка.
- Не писать в `pos` узла из HUD или обработчика клика: обработчик ставит холодное
  намерение (`hero.target?`), а `step` его исполняет. Иначе физика и ввод
  начнут спорить внутри одного кадра.
- Не оставлять `console.log` и отладочные оверлеи в движке. Статистика кадра это
  свойство `draw.stat()`, которое демо показывает в подвале, как `bog/game`.
