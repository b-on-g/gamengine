# $bog_gamengine — как писать код

Общие правила мола в `bog/mol_skill/references/STYLE.md`: имена, отсутствие
комментариев, коммиты `$bog_gamengine_x: что изменилось`, дерево делает максимум.
Здесь только то, что добавляет движок.

## Холодное и горячее

Прежде чем завести свойство, ответь: это вещь или масса?

- Вещь: `@$mol_mem` в `$mol_object2`, читается кем угодно, пишется из `step`.
- Масса: элемент `Float32Array` в `batch`, читается только `draw`, пишется в `fill`.

Признак ошибки: `@$mol_mem_key` с числовым ключом на тысячу значений. Это масса,
переноси в буфер.

## Горячий путь без аллокаций

Внутри `step`, `fill`, `phys.step` и функций `vec`:

- ни `new`, ни литералов массивов и объектов, ни `.map`/`.filter`/spread;
- результат пишется в переданный `out`, функция возвращает его же;
- циклы `for` по индексу, не `for of` по итератору;
- временные векторы это поля класса, созданные один раз.

```ts
step( dt: number ) {
	const vel = this.vel()
	const pos = this.pos()
	$bog_gamengine_vec_scale( this.tmp, vel, dt )
	$bog_gamengine_vec_add( pos, pos, this.tmp )
	this.pos( pos )
}
```

Вне горячего пути обычный мол: аллокации в мемо не страшны, они один раз.

## Правка на месте и мемо

`this.pos( pos )` с той же ссылкой инвалидацию не даст. Это осознанно для горячего
пути. Если свойство читает HUD или другой холодный узел, пиши новую ссылку или
держи рядом счётчик версии. Правило: **позиция героя это новый `Float32Array` на
запись, позиции пуль это правка буфера батча.**

Запись в атом стоит около микросекунды (спайк S2), и это не аллокация, а сам путь
записи. Для десятков узлов на кадр это ничего, для тысяч это весь бюджет. Если
объектов с `step`, пишущим в атомы, стало больше сотен, они переезжают в батч.

Атом, который читают только из `step`, будет смётан между кадрами (архитектура,
раздел 5). Нажатые клавиши, оси геймпада, положение указателя, любой опрос ввода
это поля объекта (`Map`, `Float32Array`), а не `@$mol_mem`. Атомом остаётся то, что
кто-то читает снаружи: HUD, другой холодный узел, списки сцены.

## GL только в `draw`

`gl.` встречается в `draw` и нигде больше. `shader` отдаёт строки, `shape` отдаёт
массивы, `atlas` отдаёт картинки, `batch` отдаёт буферы. Кто хочет нарисовать
что-то новое, добавляет шейдер и фигуру, а не draw-вызов.

Внутри `draw` GL-объекты создаются только в мемо по ключу и никогда внутри
`paint()`. `paint()` только выставляет состояние, заливает буферы и рисует.

## Шейдеры

- Точка входа программы это строка в `vert()`/`frag()` класса шейдера. В `.glsl`
  файлы точки входа не кладут, причина в архитектуре, раздел 3.1.
- `.glsl` файлы только в `glsl/`, без `.vert.`/`.frag.` в имени, только функции с
  аргументами, без обращения к юниформам и атрибутам. Имя функции с префиксом
  `bog_gamengine_`, а параметры и локальные без подчёркивания: сборщик читает любое
  `слово_слово` в `.glsl` как путь модуля и падает на `Root package not found`.
- В префикс программы подмешивается только `$mol_3d_glsl_both`. Строки
  `$mol_3d_glsl_vert` и `$mol_3d_glsl_frag` не трогать.
- Панель `draw` никогда не корень страницы: корень это `$mol_view` или `$mol_page`,
  панель внутри `sub`. Корневой класс получает `<body>`, а холсту нужен `<canvas>`.
- Имена в `face` в `snake_case`: `proj`, `view`, `vertex`, `uv`, `normal`,
  `inst_*`, `pipe_*`, `color`.
- `face` объявляется `as const`, тип программы выводится из него, строковые ключи
  в `glob()`/`param()` проверяет компилятор.

## Узлы и дерево

Сцена демо описывается в `view.tree`, как любой мол-компонент:

```tree
Scene $bog_gamengine_scene
	kids /
		<= Hero $bog_gamengine_sprite
			atlas <= Atlas
			frame \hero
			pos? <=> hero_pos?
		<= Coin* $bog_gamengine_sprite
			atlas <= Atlas
			frame \coin
			pos <= coin_pos*
```

Логика поведения это `step( dt )` в `.ts` наследника узла, не колбэк в дереве.
Узел не знает про ввод напрямую: он читает `input.action( 'jump' )`, а кто и как
это действие включает, решает приложение.

Никаких `.make({})` с замыканиями внутри `step`: узлы создаются деревом или
`@$mol_mem_key` фабрикой, как `Coin*`.

## Единицы

Метры, секунды, радианы. Скорость в единицах в секунду, умножается на `dt`.
Число «за кадр» в коде это ошибка.

## Тесты

- Один тест на одно утверждение, имя теста и есть описание.
- Математика и физика тестируются в ноде через `$mol_assert_equal` с округлением
  до 1e-6 там, где есть тригонометрия.
- Рендер через `bog/probe`, только цвет пикселя и счётчики вызовов, никаких
  скриншотов.
- Тест не трогает `document.body` (см. память о демке, пустеющей на `test.html`).

## Что не делать

- Не заводить `index.html` нигде, кроме `demo/`.
- Не тащить `$mol_3d_*` напрямую в `demo`: если демо чего-то не хватает в движке,
  добавляется модуль движка.
- Не писать в `pos` узла из HUD или обработчика клика: обработчик ставит холодное
  намерение (`hero.target?`), а `step` его исполняет. Иначе физика и ввод
  начнут спорить внутри одного кадра.
- Не оставлять `console.log` и отладочные оверлеи в движке. Статистика кадра это
  свойство `draw.stat()`, которое демо показывает в подвале, как `bog/game`.

## Физическое тело в дереве

У узла, чьи `pos`, `rot` или `vel` пишет физика или шаг, свойство объявляется
**двусторонним**:

```tree
Enemy* $bog_jumper_enemy
	pos? <=> enemy_pos*? Float32Array
```

Одностороннее `pos <= enemy_pos*` превращает свойство в геттер, и запись из
`phys.move` глотается без ошибки: тело считает скорость, рисуется, но стоит на
месте. Node-тесты это не ловят, потому что в них тело создают напрямую, а не
деревом. Нашлось в платформере (`bog/jumper`) одноразовым прогоном в браузере.

## Поле-буфер наружу

Метод, отдающий поле `Float32Array`, объявляется с явным типом возврата
(`Float32Array | null`), иначе TypeScript выводит узкий `Float32Array<ArrayBuffer>`
от поля, а дерево потребителя ждёт широкий `ArrayBufferLike`, и проверка типов в
сгенерированном `.d.ts` падает. Грабля общая для любого поля-буфера, которое узел
отдаёт наружу.

## Вектор из дерева

Свойство-вектор (`tile` у плоскости, `pos`, `fog`) задаётся из дерева биндингом на
метод с типом: `tile <= floor_tile Float32Array`. Список литералов `tile / 12 9` даёт
`number[]`, и переопределение не сходится по типу с `Float32Array` базового класса.

## Строковое свойство ради дерева: проверка у потребителя, не в аксессоре

Свойство с узким набором значений (`plane` у карты) иногда расширяют до `string`, чтобы
литерал писался в дереве одной строкой вместо трёх строк TS с типизированным методом.
Тогда страховкой от опечатки остаётся только рантайм, и ставить её надо **в метод,
который значение разбирает**, а не в сам аксессор: литерал в дереве генерирует
`plane(){ return "xz" }` поверх базового метода, то есть проверка внутри базового
аксессора не выполнится никогда, а установка из дерева — ровно тот путь, где опечатка
и случается. Заодно убрать молчаливую ветку `else`: неизвестное значение бросает с
перечислением известных. Тест ставит значение тем же способом, каким его ставит
сгенерированный `view.tree` (`Object.assign( obj, { plane: ()=> 'zx' } )`), иначе он
сторожит не тот путь.

## Компонент на узле

Бой, мозги и скин это компоненты: владелец вешает их свойством, а не наследует. У
компонента `owner` объявляется **обычным методом поверх поля**, не через `@$mol_mem`.
Взаимное владение (узел клеймит компонент, компонент узел) уводит обращение к
контексту в бесконечную рекурсию. В дереве это не всплывает, потому что оба объекта
уже принадлежат приложению, а на голых объектах в тесте падает сразу.

## Время в тестах целыми

`clock.time( 0.3 )` минус метка `0.2` даёт `0.0999…`, и перезарядка `0.1` не
срабатывает. В тестах время гонять целыми числами, а сравнения времени в движке
делать с допуском.
